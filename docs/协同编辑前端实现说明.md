# 协同编辑前端实现说明

> 适用页面：`src/yun-picture-frontend/src/pages/document/DocumentEditPage.vue`
> 入口页面：`src/yun-picture-frontend/src/pages/picture/AddPicturePage.vue`
> 后端对接：`src/main/java/com/zzx/yunpicturebackend/manager/websocket/DocumentEditHandler.java`

---

## 1. 功能定位

云网盘内的文本文件（txt / md / json / xml / csv / rtf）支持**多人实时协同编辑**：
- 多人同时打开同一文档，修改实时同步；
- 右侧面板展示在线编辑者头像/名单；
- 最后一个人离开时自动保存，也可手动保存。

技术方案：**前端 Yjs（CRDT 算法）+ CodeMirror 编辑器 + 后端 WebSocket 纯中继**。
后端不理解 Yjs 协议，只负责把二进制增量转发给同文档的其他客户端，保证"后端零状态、可水平扩展"。

---

## 2. 入口分发（AddPicturePage.vue）

协同编辑**不是唯一编辑方式**，按空间类型分发，避免过度设计：

```
文件已上传
 ├─ 是否纯文本 (txt/md/json/xml/csv/rtf)？ ── 否 ──> 不支持内容编辑
 └─ 是
     ├─ 团队空间/社区空间（多人）──> 跳转 /document/edit/:id 协同编辑页
     └─ 私有/公共空间（单人）  ──> REST 弹窗编辑（getFileContent / saveFileContent）
```

关键点：
- `isEditableContent`（AddPicturePage.vue:230）—— 白名单判断，docx 等办公格式会丢样式，明确不支持；
- `isMultiUserSpace`（AddPicturePage.vue:277）—— `spaceType === 1 || 2` 才走协同页；
- **单人场景用简单 REST，多人场景才上协同**，按需引入复杂度。

## 3. 技术栈

| 库 | 作用 |
|---|---|
| `yjs` | CRDT 协同算法，管理文档状态、冲突自动合并 |
| `codemirror`（v6） | 文本编辑器 |
| `y-codemirror.next` | 把 Yjs 的 `Y.Text` 绑定到 CodeMirror，双向同步 |
| 原生 WebSocket | 与后端通信（二进制 = Yjs 增量，文本 = 控制信令） |

## 4. 初始化流程（startCollaborativeEditing）

```
1. REST 拉取文件内容（getFileContentUsingGet）作为"后备"内容
2. 创建 Y.Doc，获取 ytext = ydoc.getText('content')
3. 监听 ydoc 'update' 事件 → 仅本地变更通过 WS 广播
4. 建立 WebSocket 连接（ws://.../ws/document/edit?fileId=xxx）
```

### 4.1 防回声：origin 标记（核心）

```ts
const updateHandler = (update, origin) => {
  // 远程来的增量（WebSocket 收到 / 状态同步应用）不再回发，避免循环广播
  if (origin === 'remote' || origin === 'state-sync') return
  ws.send(update)   // 只有本地编辑产生的增量才广播
}
ydoc.on('update', updateHandler)
```

`Y.applyUpdate(ydoc, data, 'remote')` / `... , 'state-sync'` 传了 origin 标记，
前端自己区分消息来源，**后端无需做任何去重**。

### 4.2 WS 地址从 REST baseURL 推导

```ts
const wsBase = (request.defaults.baseURL || window.location.origin)
  .replace(/\/$/, '').replace(/^http/i, 'ws') + '/api'
```

**不写死 localhost**：保证非本机部署、前后端分离环境也能连到正确后端。

## 5. 消息处理

### 5.1 连接成功后的"双保险"初始化

```ts
ws.onopen = () => {
  // ① 立即发 state_request，每 2 秒重试（等老客户端回快照）
  // ② 6 秒超时仍没同步到 → 判定自己是第一个编辑者
  //    → 用 REST 内容直接初始化本地编辑器，不再干等
  //    → 之后若才收到 state_response，Yjs 合并（本地无变更，不冲突）
}
```

- **2 秒重试**：兜底"首条请求与后端会话注册时序差"导致的状态丢失；
- **6 秒降级**：保证第一个编辑者不会被"永远等不到状态"卡死。

### 5.2 消息分流（与后端双通道一一对应）

```ts
ws.onmessage = (event) => {
  if (event.data instanceof ArrayBuffer) {
    Y.applyUpdate(ydoc, new Uint8Array(event.data), 'remote')   // 二进制：Yjs 增量
  } else {
    handleControlMessage(JSON.parse(event.data))                // 文本：控制信令
  }
}
```

### 5.3 控制消息处理（handleControlMessage）

| 消息 | 前端行为 |
|---|---|
| `user_list` | 更新右侧在线用户列表 |
| `join` | 若自己已初始化，把 `encodeStateAsUpdate(ydoc)` **base64** 编码后发 `state_response` 给新用户 |
| `state_request` | 定向回复自己的完整状态（`targetUserId = fromUserId`） |
| `leave` | 从用户列表移除该用户 |
| `state_response` | 解码 base64 → `applyUpdate`（标记 `state-sync`）→ `contentLoaded = true` → 未初始化则用协同状态初始化编辑器 |

### 5.4 base64 编码（体积优化）

```ts
// Yjs 状态转 base64：比 JSON 数字数组体积小约 3 倍，
// 规避 WebSocket 文本消息缓冲（默认 8KB）超限断连问题
bytesToBase64(bytes)   // 分批 (0x8000 chunk) 编码，避免调用栈溢出
base64ToBytes(base64)
```

## 6. 状态同步时序（核心场景：新用户加入）

```
前端B(新加入)              后端(纯中继)                前端A(已在编辑)
   │ state_request              │                          │
   ├───────────────────────────>│ 附 fromUserId=B 后转发    │
   │                            ├─────────────────────────>│
   │                            │ state_response           │
   │                            │ (targetUserId=B,         │
   │                            │  state=base64快照)        │
   │                            │<─────────────────────────┤
   │ sendToUser 定向转发         │                          │
   │<───────────────────────────┤                          │
   │ base64解码 → applyUpdate    │                          │
   │ → 全文恢复 → initEditor('') │                          │
```

- **为什么让"老客户端"回复快照**：后端不存文档状态，只有正在编辑的人手里有最新状态，让持状态者直接给快照，后端零存储；
- **为什么 base64**：控制消息走文本通道，编码后体积小、可 JSON 传输。

## 7. 保存策略（三条通道 + 防空覆盖）

| 通道 | 时机 | 实现 |
|---|---|---|
| 定时缓存 | 每 5 秒 | `ws.send({type:'save', content: ytext.toString()})` → 后端写内存缓存 contentBuffer |
| 最终保存 | 页面卸载 `onBeforeUnmount` | 补发一次 save（尽力而为，后端在最后一人离开时写 COS） |
| 手动保存 | 用户点「保存」 | 直接走 REST `saveFileContentUsingPost` 立即落库 |

**防空覆盖保护（重要）**：
```ts
let contentLoaded = false  // 内容是否已成功加载（REST 或协同同步）
// 未加载成功前禁止保存，避免用空内容覆盖文件
if (!contentLoaded) { message.warning('内容尚未加载成功，保存会清空文件，已拦截'); return }
```

> 空内容覆盖真实文件是最容易发生的生产事故，用标志位提前拦截，保证数据安全。

## 8. 前后端契约对照

| 后端行为（DocumentEditHandler） | 前端对应（DocumentEditPage） |
|---|---|
| 广播 `user_list` | `users.value = msg.users` 刷新面板 |
| 转发二进制 Yjs 增量 | `applyUpdate(ydoc, bytes, 'remote')` 合并渲染 |
| 转发 `state_request` | 已初始化者回 `state_response`（base64 快照） |
| 定向转 `state_response` | 新客户端应用快照 → `initEditor('')` |
| 缓存 `contentBuffer` | 每 5s 发 `save` + 卸载时补发 |
| 最后一人离开写 COS | 前端尽力发完最后一条 save |

## 9. 面试讲解要点（30 秒浓缩版）

> "协同编辑我采用 **Yjs + CodeMirror + WebSocket 中继** 的架构：前端 Yjs 管文档一致性（CRDT 自动合并冲突），后端只做信号员——转发二进制增量、中转状态同步请求。几个关键设计：
> 1. **origin 标记防回声**，本地/远程变更区分，不重复广播；
> 2. **REST 后备 + 协同同步双通道**，2 秒重试 state_request、6 秒超时降级，保证第一个编辑者不卡死；
> 3. **base64 编码状态快照**，体积小 3 倍，规避 WS 缓冲限制；
> 4. **contentLoaded 防空覆盖**，内容没加载成功就禁保存；
> 5. 保存走三条通道（5s 定时缓存 / 卸载补发 / 手动 REST 落库），最后一人离开时后端才写 COS。"

## 10. 已知短板与可优化点（面试被追问时的预案）

1. **内容只在最后一人离开时写 COS**：进程崩溃会丢 `contentBuffer`。
   优化：定时落盘（如每 30s）+ 完整 Yjs 二进制快照（`encodeStateAsUpdate`）落 COS，恢复时 `applyUpdate` 更完整。
2. **会话存单机内存**（`documentSessions` / `contentBuffer`）：多实例部署时跨节点无法互转。
   优化：转发升级为 Redis Pub/Sub 或 MQ 房间广播，各节点订阅同一主题再转发给本地 session。
3. **无服务端心跳**：前端 5s save 消息兼当心跳，静默断网时后端无法及时感知。
   优化：服务端定时 ping / 前端 pong 保活 + 超时清理。
4. **无权限二次校验（连接后）**：握手已校验，但长连接期间无会话级鉴权刷新。
