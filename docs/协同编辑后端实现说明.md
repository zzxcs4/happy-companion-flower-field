# 协同编辑后端实现说明

> 核心类：`src/main/java/com/zzx/yunpicturebackend/manager/websocket/DocumentEditHandler.java`
> 握手鉴权：`src/main/java/com/zzx/yunpicturebackend/manager/websocket/DocumentEditHandshakeInterceptor.java`
> 端点注册：`src/main/java/com/zzx/yunpicturebackend/manager/websocket/WebSocketConfig.java`
> 前端对接：`src/yun-picture-frontend/src/pages/document/DocumentEditPage.vue`

---

## 1. 后端角色定位

后端在协同编辑里**不做"大脑"，只做"信号员"**：

- 不理解、不解析、不存储 Yjs 文档内容；
- 只维护"文档房间"里的会话关系，以及消息的**转发 / 定向**。

业务动机（面试必讲）：
1. **职责分离**：正确性交给前端的 Yjs CRDT 算法，后端只管连通性；
2. **协议中立**：今天用 Yjs，明天换 Automerge / OT，后端一行不改；
3. **内容无状态**：可水平扩展，不随并发编辑文档数线性吃内存；
4. **低延迟**：纯转发 O(n)，无服务端合并的开销。

---

## 2. 核心数据结构

```java
// key: fileId, value: 该文档所有在线会话（线程安全）
private final Map<Long, Set<WebSocketSession>> documentSessions = new ConcurrentHashMap<>();

// key: fileId, value: 文档最新文本内容（内存缓存，最后一人离开时写 COS）
private final Map<Long, String> contentBuffer = new ConcurrentHashMap<>();
```

- 会话集合用 `ConcurrentHashMap.newKeySet()`，保证多线程下增删安全；
- 后端对内容唯一的存储是 `contentBuffer`（只存最新文本），不存 Yjs 增量。

## 3. 握手鉴权（DocumentEditHandshakeInterceptor）

端点：`ws://.../ws/document/edit?fileId=xxx`，握手 5 步校验，**任一步失败 `return false` 拒绝建立连接**：

1. **参数校验** — `fileId` 非空；
2. **登录校验** — `userService.getLoginUser()` 非空；
3. **文件存在** — `fileService.getById(fileId)` 非空；
4. **类型白名单** — 扩展名必须是 `txt / md / json / xml / csv / rtf`；
5. **空间权限** — 私密空间拒绝；非私密空间校验 `PICTURE_EDIT` 权限。

校验通过后把上下文塞进 attributes，供 Handler 使用：

```java
attributes.put("user", loginUser);
attributes.put("userId", loginUser.getId());
attributes.put("fileId", Long.valueOf(fileId));
```

> 设计点：**安全关口放在握手，内容关口完全放开**。连接建立后内容透明，安全在连接前就挡住。

## 4. 连接生命周期

### 4.1 连接建立（afterConnectionEstablished）

```
客户端A连接成功
 ├─ 1. documentSessions[fileId].add(sessionA)
 ├─ 2. 广播 join 消息（含 user 信息）给同文档【其他】客户端（排除自己）
 └─ 3. 向该文档【所有】客户端广播最新 user_list（保证先到者也能看到后来者）
```

设计点：join **排除自己**（自己能看到自己加入没意义）+ user_list **群发**（用户列表要一致）。

### 4.2 连接关闭（afterConnectionClosed）

```
客户端A断开
 ├─ 1. documentSessions[fileId].remove(sessionA)
 ├─ 2. 若该文档会话集合已空：
 │      ├─ 从 contentBuffer 取出最新内容
 │      └─ saveContentToCos()：临时文件 → COS 覆盖原文件
 ├─ 3. 广播 leave 消息给剩余客户端
 └─ 4. 重新广播 user_list（刷新在线列表）
```

落盘策略：**平时只写内存缓存，最后一人离开时才写 COS**——批量写、延迟写，避免每次编辑都打对象存储。

---

## 5. 消息处理（双通道）

Handler 继承 `AbstractWebSocketHandler`，天然区分二进制与文本两类消息。

### 5.1 二进制通道：Yjs 增量（handleBinaryMessage）

```
客户端A ──[二进制: Yjs update]──> DocumentEditHandler
   └─ 原样中继给同文档其他客户端（排除 A）
客户端B <──[二进制: Yjs update]──
```

**不做任何解析、不落库**——"后端瘦"的核心。

### 5.2 文本通道：控制信令（handleTextMessage）

| type | 谁发 | 后端动作 |
|---|---|---|
| `save` | 客户端（每 5s + 卸载时） | 只更新 `contentBuffer[fileId]`（内存），不落盘 |
| `state_request` | 新加入客户端 | 附 `fromUserId` 后**转发**给同文档其他客户端 |
| `state_response` | 已在编辑客户端 | 按 `targetUserId` **定向转发**（sendToUser） |

## 6. 新用户加入的状态同步（核心时序）

```
前端B(新加入)            后端(信号员)                前端A(已在编辑)
   │ state_request            │                         │
   ├─────────────────────────>│ 附 fromUserId=B 后转发   │
   │                          ├────────────────────────>│
   │                          │ state_response         │
   │                          │ (targetUserId=B,       │
   │                          │  state=base64快照)      │
   │                          │<────────────────────────┤
   │ sendToUser 定向转发       │                         │
   │<─────────────────────────┤                         │
   │ applyUpdate → 恢复全文     │                         │
```

设计要点：
- **让"老客户端"回复快照**——后端不存文档状态，只有持有状态的人才能给快照，后端零存储；
- **前端定时重发 state_request** 兜底"首条请求与后端会话注册时序差"导致的丢失（`DocumentEditHandler.java` 第 151-154 行注释）；
- `sendToUser` 通过 `userId` 在文档会话组里找对应 session 定向发送。

---

## 7. 落盘策略

- **定时缓存**：前端每 5s 发 `save` → 存入内存 `contentBuffer`；
- **最终落盘**：最后一人离开时，把 `contentBuffer` 的内容写入 COS（覆盖原文件，`saveContentToCos` 第 264-287 行）：
  1. 从文件 URL 提取 COS key；
  2. 内容字节写临时文件；
  3. `cosManager.putObject(key, tempFile)` 上传；
  4. `finally` 删除临时文件。

---

## 8. 与前端契约对照

| 后端行为 | 前端对应 |
|---|---|
| 广播 `user_list` | `users.value = msg.users` 刷新面板 |
| 转发二进制 Yjs 增量 | `applyUpdate(ydoc, bytes, 'remote')` 合并渲染 |
| 转发 `state_request` | 已初始化者回 `state_response`（base64 快照） |
| 定向转 `state_response` | 新客户端应用快照 → `initEditor('')` |
| 缓存 `contentBuffer` | 每 5s 发 `save` + 卸载时补发 |
| 最后一人离开写 COS | 前端尽力发完最后一条 save |

## 9. 面试讲解要点（30 秒浓缩版）

> "文档协同的后端我设计成**信号员**：不理解 Yjs 协议，只负责把二进制增量转发给同文档其他客户端，把新用户的状态请求转发给老用户、再把老用户回传的快照定向转发回去。后端内容上无状态，能水平扩展，换前端协议也不用改后端。落盘走的是'最后一个人离开时才写 COS'的延迟批量策略，平时只放内存缓存。安全全在握手阶段做（登录 + 文件类型白名单 + 空间权限）。"

## 10. 已知短板与可优化点（面试预案）

1. **内容只在最后一人离开时写 COS** — 进程崩溃丢 `contentBuffer`。
   优化：定时落盘（如每 30s）+ 完整 Yjs 二进制快照落 COS，恢复时 `applyUpdate` 更完整。
2. **会话存单机内存** — 多实例部署无法跨节点互通。
   优化：转发升级为 Redis Pub/Sub 或 MQ 房间广播，各节点订阅同一主题再转发本地 session。
3. **`John` 无服务端心跳** — 靠前端 5s save 兼当心跳，静默断网难以及时感知。
   优化：服务端定时 ping / 前端 pong 保活 + 超时清理。
4. **内容控制信令无长度/频率限制** — 可被恶意刷屏。
   优化：消息报文大小限制 + 频率限流 + 校验 user 是否为正则编辑成员。
